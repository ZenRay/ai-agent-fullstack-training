# 收尾设计

编号文档已经分别写过失败事件、断线、取消、模型流中断和进程重启。这篇补上还没写清的两处：循环停了却没有终态，以及写工具超时后结果不明。

依据：

- [AG-UI：运行必须以完成或错误结束](https://docs.ag-ui.com/spec/1.0/events/lifecycle)
- [AG-UI：没有终态的流会被当成成功](https://github.com/ag-ui-protocol/ag-ui/issues/2300)
- [超时不是重试的许可](https://upcube.ai/resources/research/unknown-effects)
- [写工具的幂等与对账](https://edilec.com/blog/ai-11008/idempotent-agent-tool-calls/)
- [结果不明时先查下游](https://gawrys.me/blog/reconciling-ambiguous-ai-tool-outcomes/)

人工确认、多 Agent 路由、多进程 Redis，总说明放在这 10 步之后，这篇不展开。

## 概念

已经落进编号文档的部分：

| 已有约定 | 落在 |
| --- | --- |
| 失败事件的字段、取消单独成终态 | `docs/02-RunEvent设计.md`、`docs/04-StreamingModel设计.md` |
| 客户端 SSE 断开，run 继续 | `docs/03-SSE设计.md`、`docs/08-创建运行与取消接口设计.md`、`docs/09-客户端设计.md` |
| 用户取消 | `docs/08-创建运行与取消接口设计.md`、`docs/07-AgentLoop与工具注册设计.md` |
| 模型流中途断开、可见内容前后的重试 | `docs/04-StreamingModel设计.md`、`docs/05-模型网关设计.md` |
| 进程重启后的检查点 | `docs/11-数据库与checkpoint设计.md` |
| 上述路径的验收 | `docs/10-异常测试设计.md` |

这两件仍由服务端落进已有事件，不新增事件种类。`run.failed` 增加一个稳定的 `code`：`incomplete-stream`。工具仍用 `tool.result`。

一次 run 在日志里要么还开着，要么以 `run.completed`、`run.failed`、`run.cancelled` 之一结束。写工具的超时只说明调用方没等到响应。先按幂等键对账，再决定要不要用同一把键重试。

## 它解决什么

- 循环任务因未捕获异常退出，或模型流既没有 `model.finished` 也没有 `model.failed` 就结束时，日志停在 `message.delta` 上。下一次阅读会把半截当成完整回答。
- 订阅者关掉连接时，循环还在写。这条连接结束不能写成 `incomplete-stream`。
- 进程被杀掉时，当时没有机会写终态。下次启动按 `docs/11-数据库与checkpoint设计.md` 接上，不在退出的瞬间补事件。
- 超时之后若只返回「结果不明」、收据只在成功时写入，重启或重试看不到「已经发出去」的记录，会再发一次。
- 模型若把「结果不明」理解成「没做成」，会改一改参数再调同一个写工具。

## 设计

### 谁来补终态

只有循环这一侧知道自己已经停了。`api/` 只编码，`sse/` 只组帧。在 `execute_run` 外面套一层：任务结束时若这条 run 还没有终态事件，就追加一条 `run.failed`。

| 实际情况 | 日志 |
| --- | --- |
| 模型给出 `model.failed`，或 `length`、`content_filter` | `run.failed`，`code` 用模型给出的原因 |
| 调用方取消 | `run.cancelled` |
| 循环正常走完 | `run.completed` |
| 循环任务退出，日志里还没有上面三种 | `run.failed`，`code` 为 `incomplete-stream` |
| 某个订阅断开，或队列满了只断开慢客户端 | 不追加终态，run 继续 |
| 进程消失 | 不在当时补。下次启动按 `docs/11-数据库与checkpoint设计.md` 的表接 |

`incomplete-stream` 的 `message` 说明运行中断、已生成的文字仍在前面的 `message.delta` 里。`retryable` 在没有「结果不明」的写工具时为真；已经有一张结果为空的写收据时为假，避免整次 run 再跑一遍把写操作又送出去。用量若当时已经拿到，跟在这条 `run.failed` 上，规则与 `docs/02-RunEvent设计.md` 相同。

客户端看到连接在终态之前断开，界面保持已有文字，并按最后的 `seq` 再读。本地的「未完成」只是还没看到终态。日志里出现 `incomplete-stream` 之后，才把这次 run 显示为失败。呈现见 `docs/09-客户端设计.md`。

### 写工具的三种结果

读工具保持 `docs/07-AgentLoop与工具注册设计.md` 的约定：同一轮超时预算内可再试一次，失败写成 `tool.result`，`ok` 为假，循环继续。

写工具在调用处理函数之前先占收据。键仍是 `hash(run_id + call_id + 规范化参数)`，和 `docs/06-RunStore设计.md` 一致。收据多一个状态：

| 状态 | 含义 | 下次遇到同一键 |
| --- | --- | --- |
| 已占坑，尚无结果 | 准备发送，还不知道下游情况 | 先对账，不直接再调用 |
| 已有结果 | 下游结果已经写回 | 把这份结果当作 `tool.result`，不再发送 |
| 结果不明 | 超时、连接中断，或对账后仍无法证明 | 把「可能已经生效、不要再送」写进 `tool.result`，不再发送 |

对账只做三种判断：下游能按这把键查到结果，就写回收据并返回成功；下游能证明没有这条记录，就用同一把键再送一次；两边都证明不了，就停在结果不明。补偿动作是一次新的 `call_id`、新的键，不用来证明上一次没发生。

同一轮里，模型若再次给出相同参数的写调用，执行层读到这张收据，把同一份说明送回去。参数变了就是新的 `call_id`，新的键。前一张若仍是结果不明，`tool.result` 的说明里写明前一次可能已经生效。

取消发生在发送前：不占收据，不调用工具，直接 `run.cancelled`。取消发生在发送后：等返回或超时，先写 `tool.result`，再写 `run.cancelled`。

校验失败、未注册的名字，发生在占坑之前，只有 `tool.result`，没有收据。

## 实现方式

终态补写放在 `app/loop/`，包住 `execute_run`。Store 在追加前仍拒绝已终态的 run，因此正常结束的路径不会再被补一条失败。

收据放在 `app/store/`。内存实现用进程内的表，重启后这张表消失，和 `docs/06-RunStore设计.md` 一致。SQLite 用 `docs/11-数据库与checkpoint设计.md` 的 `effect_receipts`。`output` 为空且标记为不明时，恢复逻辑不再调用处理函数。

对账函数由写工具自己提供：给定幂等键，返回「已存在并给出结果」「确定不存在」或「无法判断」。没有这个函数的写工具，超时后直接进入结果不明，不做第二次发送。

`tests/loop/` 补两条验收：循环在第一条 `message.delta` 之后抛异常，日志以 `incomplete-stream` 结束，已有增量还在；写工具第一次超时且对账结果为无法判断，处理函数只被调用一次，第二次相同参数不再进入处理函数。订阅断开仍按 `docs/10-异常测试设计.md`，不出现这条 `code`。

## 代码

循环外面负责补终态。订阅任务不在这里。

```python
async def run_until_terminal(store, model, tools, run_id: str) -> None:
    try:
        await execute_run(store, model, tools, run_id)
    finally:
        if not has_terminal(store, run_id):
            unknown = store.has_unknown_write(run_id)
            await store.append(run_id, {
                "type": "run.failed",
                "code": "incomplete-stream",
                "message": "运行中断，已生成的内容仍保留在前面的事件里",
                "retryable": not unknown,
            })
```

写工具先占坑，超时后只对账。

```python
async def execute_write(store, tool, run_id, call_id, arguments) -> dict:
    key = hash_key(run_id, call_id, arguments)
    receipt = await store.claim_receipt(key, run_id, call_id)
    if receipt.output is not None:
        return {"ok": receipt.ok, "output": receipt.output}
    if receipt.status == "unknown":
        return {"ok": False, "output": "结果不明，可能已经生效，不要再用相同参数发送"}
    try:
        output = await asyncio.wait_for(
            tool.handler(arguments, idempotency_key=key),
            tool.timeout_seconds,
        )
    except TimeoutError:
        seen = await tool.reconcile(key)
        if seen.found:
            await store.settle_receipt(key, ok=True, output=seen.output)
            return {"ok": True, "output": seen.output}
        if seen.absent:
            output = await tool.handler(arguments, idempotency_key=key)
            await store.settle_receipt(key, ok=True, output=output)
            return {"ok": True, "output": output}
        await store.mark_unknown(key)
        return {"ok": False, "output": "超时，结果不明，不要重试这次写操作"}
    await store.settle_receipt(key, ok=True, output=output)
    return {"ok": True, "output": output}
```

对应关系：

- `claim_receipt` 在处理函数之前提交。同一键的第二个调用者看到的是同一行。
- `reconcile` 返回无法判断时，处理函数的第二次调用不会发生。
- `run_until_terminal` 不查看 SSE 连接。阅读端断开只取消订阅任务，`execute_run` 仍继续，`finally` 不会在中途补上 `incomplete-stream`。
