# 模型网关设计

模型网关是所有模型调用前面的一道门。调用方只拿虚拟密钥和公开模型名；供应商密钥、选路、限流和花费留在这道门里。Agent Gateway 管一次运行的状态、事件日志和工具，不承担这些职责。

- [LiteLLM：一次请求的路径](https://docs.litellm.ai/docs/proxy/architecture)
- [LiteLLM：重试、fallback 与冷却](https://docs.litellm.ai/docs/router/learn/reliability)
- [Microsoft 流式模型网关](https://github.com/microsoft/agenticai-design-patterns/blob/main/assets/agent-runtime/hosted-agent-streaming-model-gateway/README.md)
- [Cloudflare AI Gateway：fallback](https://developers.cloudflare.com/ai-gateway/configuration/fallbacks/)

- [llm.buzz：重试与幂等](https://llm.buzz/docs/retries-and-idempotency)

## 概念

一次模型调用从调用方进入网关，网关选定一个后端，把请求译成该供应商的格式，再把流原样推回去。调用方看到的是统一入口，常见的是 OpenAI 兼容的 `POST /v1/chat/completions`。

网关里有三个名字：

| 名字 | 谁持有 | 作用 |
| --- | --- | --- |
| 虚拟密钥 | 每个调用方一把 | 身份、可用模型、预算、速率 |
| 公开模型名 | 配置里的别名，如 `chat-default` | 调用方只写这个名字 |
| 部署 | 某一家供应商上的真实模型和密钥 | 网关内部才看得见 |

一个公开模型名背后是一组部署，称为模型组。组内可以负载均衡，组外按顺序 fallback。供应商密钥只出现在部署配置里。

Agent 侧的 `StreamingModel` 用虚拟密钥调用这个入口，再把供应商的流翻译成内部事件。翻译约定见 `docs/04-StreamingModel设计.md`。网关自己不产生 `RunEvent`。

## 它解决什么

- 密钥散落在每个 Agent 进程里，轮换和泄露范围都不好收。
- 各家的路径、事件名和工具参数形状不同，调用方要为每一家写一套客户端。
- 一家超时、429 或宕机时，调用方自己做切换，容易和 SDK 的自动重试叠在一起，打出两次生成。
- 并发请求同时通过预算检查，结算发生在响应之后，预算会被打穿。
- 流式响应一旦开始就改不了 HTTP 状态；中途换一家再写，客户端会看到两段拼起来的回答。
- 账单按供应商到账，内部看不出是哪个调用方、哪个别名、第几次尝试花的。

## 设计

一次请求按这个顺序走。花费写入和速率回写放在响应发出之后，不挡在转发路径上。

```text
调用方  虚拟密钥 + 公开模型名 + Idempotency-Key
  │
  ▼
鉴权与预算预扣
  │
  ▼
速率限制（密钥、用户、团队、整站）
  │
  ▼
路由器
  ├─ 组内：负载均衡、重试、冷却
  └─ 组间：按顺序 fallback，每一跳重新检查预算和权限
  │
  ▼
适配器  译成供应商请求，流式逐块吐出
  │
  ▼
异步记账  调用方、别名、实际模型、Token、TTFT、尝试次数、结果
```

路由分成三档，作用范围不同：

| 动作 | 范围 | 何时使用 |
| --- | --- | --- |
| 重试 | 同一个模型组，可以换一台部署 | 超时、连接中断、429、500、502、503、504 |
| fallback | 下一个模型组 | 组内重试用尽、额度耗尽、模型不存在 |
| 冷却 | 把一台部署暂时移出候选 | 连续失败或收到 `Retry-After` |

网关是唯一的重试循环，打到供应商时把 SDK 和 HTTP 客户端的自动重试关掉。429 带了 `Retry-After` 就至少等那么久，再加一小段抖动。没有这个头，用有上限的指数退避。fallback 链保持很短，每一跳都重新检查这把虚拟密钥能不能用那个模型、预算还够不够。数据区域约束在切换后仍然有效。

熔断看连续的 429、500、503。打开之后请求走备用部署，过一段时间用一个小请求探测，恢复后再放回候选。

### 换供应商的节点

换供应商按「这一次模型调用」计算，不按整次 Agent 运行计算。一次 run 里会有多次模型调用。工具结果写回之后的下一次调用是一条新请求，可以重新选供应商。

同一次流里，只有在调用方还没看到任何可见内容时才能换。Microsoft 把边界放在第一帧 `data:` 到达调用方之前。LiteLLM 在调用方还没收到内容时，把这次流当成一开始就失败，在同一模型组里重试或进入下一个 fallback。可见内容指文字或工具参数。供应商的保活帧不算，只发保活的连接仍然受首 token 超时约束。

| 此刻流里有什么 | 能否换供应商 |
| --- | --- |
| 连接还没打开，或只有 HTTP 错误 | 能。用原始消息，同一把幂等键 |
| 只有供应商保活帧，还没有文字或工具参数 | 能。首 token 超时仍然生效 |
| 已经交出文字，或已经交出工具参数 | 不能。锁定这一家，结束这次调用 |
| 工具结果已经写回，循环再次调用模型 | 能。这是下一次调用，重新选路 |

第一块内容发出去之后再换，调用方会看到两段拼在一起的回答，Token 也会算两次。

响应头可以先攒到第一个 token 再发出，这样失败仍能返回普通 JSON 错误。模型要思考很久时，改为先提交响应头并发送保活；这种模式下，之后的失败只能写在 SSE 里。客户端断开时，网关停止读取上游。

### 带工具调用

请求里带了工具时，换供应商的节点更早锁死，而且不能把半截输出拼进下一次请求。

LiteLLM 曾经在流中断后把半截助手文字拼进 fallback 请求。请求里的 `tools` 还在，备用模型却接着写散文，并返回空的 `tool_calls`。流本身显示成功，下游等着的工具调用没有发生。后来的规则是：已经出现工具调用、思考块或 JSON 模式的流，不做中途续写。纯文本续写也只是可选项，而且备用模型必须支持把已有文字当作前缀。

| 工具走到哪 | 处理 |
| --- | --- |
| 请求带了工具，但模型还没输出 | 可以换。备用模型收到原始消息和同一份工具定义 |
| 工具参数只到了一部分，还没有完整的一次调用 | 不能换，也不能执行工具。适配器不把半截参数交出去，这次调用以失败结束 |
| 已经交出完整的工具调用 | 参数到齐才执行。执行完把结果写回对话。下一次模型调用可以重新选供应商 |
| 有副作用的工具已经执行 | 不再用另一家重做这次调用。重复执行靠工具自己的幂等键挡住 |
| 内容过滤，或这次输出被要求成 JSON | 不换供应商接着写 |

半截工具参数不能当成一次调用交给另一家。各家参数增量的拼法不同，换过去要么参数对不上，要么模型放弃调工具、改成写文字。

带工具的失败因此只有两条路。还没有可见内容时，用原始消息换一家，工具定义原样带上。已经有文字或工具参数时，保留已经写下的文字，这次调用结束，不把半截回答拼进下一次提示词。Agent 侧把这次结束写成 `run.failed`，执行工具仍只发生在 `tool.arguments.done` 之后。

### 预算、幂等与观测

预算按「先占后结」：

1. 用 `max_tokens` 和价目表估算这次最多花多少，先占住。
2. 占住就会超预算，就在打到供应商之前拒绝。
3. 响应里的 usage 到达后，用实际花费替换预扣，退回多占的部分。
4. 流在 usage 到达前断开，记一条估算，并退回预扣。多副本把计数放在共享存储里。

幂等键覆盖同一次逻辑调用。相同的键和相同的请求体：第一次还在跑就等待它，已经完成就返回同一份结果，不再打供应商。请求体变了就拒绝。流式结果通常不保存回放，重复的流式请求直接拒绝。Anthropic Messages 不认这个头，同一把键在那里仍是一次新请求。会话号不能拿来当幂等键。换路由再试同一次调用时仍用这把键；工具结果写回后的下一次调用使用新键。

观测默认只记调用方、公开模型名、实际后端、尝试次数、TTFT、输入和输出 Token、缓存 Token、花费和结果。Prompt 和回答正文默认不记。网关记录回答「打到了谁、花了多少」；Agent 的事件日志回答「为什么调了这个工具」。两边用同一个 trace id 对上。

## 实现方式

入口保持 OpenAI 兼容：`/v1/chat/completions` 同时接受 JSON 和 SSE，再加 `/v1/embeddings` 和 `/v1/models`。调用方继续用原来的 SDK，只改 `base_url` 和虚拟密钥。

配置分成四份：虚拟密钥（允许的模型、预算、rpm/tpm）、模型组（公开名到部署列表）、fallback 顺序、价目表。价目表带版本，价格变动不改写历史账单。

进程内可以先做：密钥和部署放配置文件，限流和预扣放内存。多副本改为共享计数，数据库存密钥和账单。流式处理本身保持无状态，一块到了就写一块。

流式请求带上 `stream_options.include_usage`，让最后一块带上 Token。上游没有 usage 时，把这条账单标成估算。每条请求写一条 usage 记录。

本仓库的 Agent 进程不实现这道门，只做它的调用方。取消一次 Agent 运行时，由 Agent 断开这条模型连接，网关再去取消上游。

## 代码

下面是网关内部一次流式调用的骨架，用来看各层怎么交接。

```python
async def stream_completion(request, virtual_key, body, idempotency_key):
    caller = await auth.load(virtual_key)          # 密钥是否存在、允许这个模型
    fingerprint = hash_body(body)
    claim = await idempotency.claim(idempotency_key, fingerprint)
    if claim.replay:
        return claim.stored                         # 相同键和相同请求体，交还原结果

    reservation = await budget.reserve(caller, estimate(body))
    if reservation.rejected:
        raise HTTPException(402, "budget_exceeded")

    await limits.acquire(caller)                    # rpm / tpm，多副本用共享计数
    group = router.group_for(body["model"])
    saw_content = False
    try:
        async for chunk in router.open_stream(group, body):
            if await request.is_disconnected():
                await chunk.aclose_upstream()       # 调用方走了就停上游
                return
            if chunk.is_content:
                saw_content = True                  # 此后锁定这一家，不再换路由
            yield chunk                             # 到一块写一块，不攒完整回答
            if chunk.usage:
                await budget.settle(reservation, chunk.usage)
    except ProviderError as exc:
        if saw_content:
            yield sse_error(exc)                    # 已经写出内容，错误留在流里
            return
        await budget.refund(reservation)           # 还没有内容，预扣退回
        raise
    finally:
        await usage.record_async(caller, body["model"], saw_content)
```

对应关系：

- `auth.load` 和 `budget.reserve` 发生在任何供应商请求之前。并发请求各自占住一笔估算。
- `idempotency.claim` 用「键 + 请求体指纹」挡住同一次逻辑调用的第二次生成。
- `router.open_stream` 内部才做组内重试和组间 fallback，并且只在 `saw_content` 仍为假时这么做。供应商 SDK 的 `max_retries` 设为 0。请求带了工具、但还没有内容时，备用模型收到原始消息。已经出现工具参数后，这个循环不再换一家。
- `yield chunk` 是转发。网关不把供应商的事件翻译成 `RunEvent`。
- `budget.settle` 用最后一块里的 usage 替换预扣。流被掐断、usage 没到，`record_async` 把这条记成估算。
- `finally` 里的记账异步执行，不把数据库写入放在下一块内容之前。
